# Google Drive PDF Reports — Spec

Short name: `google-drive-pdf`
Status: Draft, awaiting implementation
Scope: `backend/` + `frontend/` + `docs/` (cross-boundary contract, both sides change)
Request shape: "integrate Google Drive with the system and implement PDF report generation…
generated PDFs saved to Google Drive, with header, footer, page numbers, a unique tracking number
per PDF, and a QR code for document verification"

---

## 1. Request and interpretation

> Can we integrate Google Drive with the system and implement PDF report generation? The generated
> PDF files should automatically be saved and stored in Google Drive.
>
> PDF Generation Requirements:
>
> - Header
> - Footer
> - Page numbers
> - Unique tracking number for each generated PDF
> - QR code for document verification (recommended feature), allowing users to scan the QR code to
>   verify the authenticity and validity of the generated document.

Interpreted goal: a server-side document pipeline that turns clinic records into **real PDFs**
(not the browser's print dialog), stamps every page with clinic letterhead, page numbers, a
unique tracking number and a verification QR code, stores the bytes with the issue record, files a
copy into the clinic's **Google Drive** under type/month folders, and exposes a **public,
login-free verification page** that confirms a document is genuine and still valid.

The PDF is generated by the API, not the browser. The browser only asks for a document and receives
either a download or a link to the filed copy; the QR resolves to a public route on the clinic
frontend.

| 13  | Retry durability             | **Persisted queue in MongoDB + a 5-minute scheduled job**, with attempt counts, next-retry timestamps and a final failed state.                                                                           |
| 14  | Document discovery           | **A Documents archive page** listing issued PDFs with type, tracking number, issuer, Drive status, verify link, download and retry actions.                                                               |

| 16  | Tracking number              | **Type prefix + year + zero-padded sequence**: `RPT-`, `PTS-`, `VIS-`, `RCP-` + `YYYY` + 6 digits.                                                                                                       |

Two decisions need a note for the implementer:

- **#6 is a substitution, not a preference change.** FPDF/mPDF are PHP packages (`fpdf.org`,
  `mpdf.github.io`) with no Node runtime. Do not add a PHP sidecar just for this. pdfkit gives the
  same "draw the page in code" model the requester asked for, with header/footer/page-number control
  and no browser binary on the VPS.
- **#11 removes the "clinical copy" option** offered in the interview. If a therapist needs full
  clinical notes, that is a separate internal document type for a later spec, not a variant of the
  patient summary.

## 3. Research findings

### 3.1 Google Drive authentication

| Fact | Detail | Consequence |
| ---- | ------ | ----------- |
| Service accounts cannot own files | Google: "Service accounts don't have storage quota and can't own files. Instead, they must upload files and folders into shared drives, or use OAuth 2.0." | Confirms decision #2. A service account would require a Workspace shared drive, which this clinic does not have. |
| `drive.file` is the narrow, non-sensitive scope | `https://www.googleapis.com/auth/drive.file` allows creating files the app opens/creates; it is not a restricted scope and needs no security assessment. | Use it. Avoid `auth/drive`, which is restricted and requires OAuth app verification for public use. |
| `drive.file` cannot see arbitrary folders | The scope only exposes files the app created (or the user picked via Google Picker). A folder ID copied from a user's My Drive will 404. | The root folder must be **created by the app** (default). A pre-existing folder ID is only accepted if this app created it earlier. Document this in the integration card. |
| Refresh tokens in "Testing" publishing status expire after 7 days | Google OAuth apps left in Testing issue short-lived refresh tokens. | The Google Cloud OAuth consent screen must be **published to In production** for the Drive connection to survive. Put this in the setup guide. |
| Files owned by the connected user | With OAuth on behalf of the clinic account, the clinic account owns the files and its Drive quota is consumed. | Correct ownership for a clinic: documents survive staff turnover as long as the clinic account remains. |
| Upload API | `POST https://www.googleapis.com/upload/drive/v3/files?uploadType=multipart&supportsAllDrives=true&fields=id,webViewLink,name,size` with a `multipart/related` body: JSON metadata part + `application/pdf` media part. | No `googleapis` SDK needed; the codebase already talks to Google over raw `fetch` in `calendarService.ts`. Keep that pattern. |
| Folder search | `GET https://www.googleapis.com/drive/v3/files?q=name = '<name>' and '<parent>' in parents and mimeType = 'application/vnd.google-apps.folder' and trashed = false&fields=files(id,name)` | Used to reuse a month folder instead of creating duplicates. |
| Error codes | `401` invalid/revoked token, `403` `storageQuotaExceeded` or `insufficientFilePermissions`, `404` folder/file missing, `429` rate limit, `5xx` provider. | Drives the failure classification in §12.6. |

### 3.2 PDF generation in Node

| Option | Verdict |
| ------ | ------- |
| **pdfkit** (chosen) | Programmatic layout with explicit header/footer, real TTF embedding, streaming/buffered output, ~1 dependency, no native build on Windows or Linux. Best fit for a fixed clinical letterhead. |
| Puppeteer / headless Chrome | Best visual parity with the existing React Reports page, but adds a ~300 MB Chromium to the VPS and 50–100 ms per render. Rejected because the portal stays small and self-hosted. |
| `@react-pdf/renderer` | No browser, but it introduces a second styling model beside Tailwind and complicates shared branding. Rejected. |
| `pdf-lib` | Manipulation, not generation; would still need a generator. Not used. |

QR codes: `qrcode` (npm) renders a PNG buffer server-side (`QRCode.toBuffer(url, { type: "png", margin: 1, width: 180, errorCorrectionLevel: "M" })`), which pdfkit embeds with `doc.image()`. Do not generate the QR in the browser — the PDF must be correct before it ever reaches a browser.

### 3.3 Page numbering with pdfkit

`new PDFDocument({ bufferPages: true })`; after content is written, read
`doc.bufferedPageRange()` and, for each page, `doc.switchToPage(i)` and draw the footer with
`Page ${i + 1} of ${count}`. This is the only reliable way to know the total, and it lets the full
header/footer band repeat on every page (decision #19).

## 5. Goals / non-goals

### Goals

1. Generate four document types as real PDFs from server data, with identical letterhead rules across all four.
2. Stamp every page with clinic identity, page X of Y, tracking number, issue metadata and a verification QR.
3. Allocate collision-free, human-readable tracking numbers per type per year.
4. File every PDF into the clinic's Google Drive under type/month folders, with a durable retry queue.
5. Let anyone verify a document at a public URL without a login, and show superseded/revoked states truthfully.
6. Never place a patient name or clinical note on the public verification page, in a Drive filename, or in Drive metadata.
7. Give staff an archive of issued documents with download, Drive link, verify link and retry.
8. Degrade cleanly: no Drive connection → documents still generate and download; Drive errors never lose a document.

### Non-goals

- Automatic generation on appointment completion, monthly cron reports, or bulk backfill of historical documents.
- Patient-facing document access in the portal.
- Google Picker, shared drives, domain-wide delegation, service accounts.
- PDF/A archival conformance, cryptographic PDF signatures (the QR + tracking record is the verification mechanism).
- Editing an issued PDF, or storing multiple versions under one tracking number.
- Emailing PDFs to patients (the existing mailer is untouched; staff can attach a downloaded copy manually).
- OCR, Excel export, or replacing the existing CSV payments export.

## 6. Architecture

```
Staff click "Generate PDF"
  → POST /documents (protectRoute + role check)
      → documentService.createDocument()
          1. resolve template data (read-only Mongoose queries)
          2. allocate tracking number (DocumentCounter, atomic $inc)
          3. render PDF buffer (pdfkit + qrcode)
          4. compute sha256, size; persist GeneratedDocument (drive.status = "pending")
          5. attempt Drive upload once, inline, 10 s timeout
          6. respond 201 with document metadata
  → frontend shows success toast + Documents link; download is available immediately

Drive upload failure
  → record stays drive.status = "pending" with attempts/nextAttemptAt
  → documentSyncJob (setInterval 5 min) retries up to 5 times with backoff
  → after 5 failures: drive.status = "failed" (manual Retry from Documents, admin/secretary)

Public verification
  → GET /verify/:trackingNumber (no auth, rate-limited)
      → GeneratedDocument lookup by trackingNumber (indexed)
      → minimal JSON: status, type, tracking, issuedAt, clinicName, supersededBy/revokedAt
  → frontend /verify/:trackingNumber renders the result on the public paper-and-pine page
```

Layering follows `AGENTS.md`: routes wire middleware + controllers; controllers parse Zod schemas
and call services; services own Mongoose and never touch `req`/`res`; models only describe data.
PDF bytes never travel through a controller's `res.json`.

## 7. Data model

### 7.1 `GeneratedDocument` (`backend/src/models/generatedDocumentModel.ts`)

```ts
export type DocumentType = "clinic_report" | "patient_summary" | "visit_record" | "receipt";
export type DocumentStatus = "issued" | "superseded" | "revoked";
export type DriveStatus = "pending" | "uploaded" | "failed";

export interface DocumentDriveState {
  status: DriveStatus;
  fileId: string;
  webViewLink: string;
  folderId: string;
  attempts: number;
  lastError: string;
  lastAttemptAt: Date | null;
  nextAttemptAt: Date | null;
  uploadedAt: Date | null;
}

export interface GeneratedDocument {
  trackingNumber: string;      // unique, immutable
  type: DocumentType;
  title: string;               // e.g. "Clinic activity report · October 2026"
  status: DocumentStatus;
  fileId: string;              // stable uuid used in the Drive filename
  fileName: string;            // "<tracking>_<yyyy-mm-dd>.pdf", no patient name
  mimeType: "application/pdf";
  sizeBytes: number;
  sha256: string;
  pdf: Buffer;                 // the file itself; select: false
  patient: Types.ObjectId | null;
  dependent: Types.ObjectId | null;
  appointment: Types.ObjectId | null;
  rangeFrom: Date | null;
  rangeTo: Date | null;
  generatedBy: Types.ObjectId;
  generatedByRole: "admin" | "secretary" | "therapist";
  generatedByName: string;     // snapshot; survives user rename/archive
  supersedes: Types.ObjectId | null;
  supersededBy: Types.ObjectId | null;
  revokedAt: Date | null;
  revokedBy: Types.ObjectId | null;
  revokeReason: string;
  drive: DocumentDriveState;
  createdAt: Date;
  updatedAt: Date;
}
```

Rules:

- `pdf` is `select: false` so list endpoints never ship bytes; the download endpoint explicitly
  `.select("+pdf")`.
- `trackingNumber` has a unique index. `status` changes are append-only in spirit: `issued →
  superseded` and `issued → revoked`; nothing returns to `issued`.
- A 10 MB BSON guard: rendering throws `DocumentTooLargeError` above 10 MB (the Mongo document
  limit is 16 MB; a clinic report is typically 60–250 KB). Do not stream to GridFS for v1.
- `generatedByName` is a snapshot, not a populate, so an archived staff account cannot blank the
  issuer line on an existing document.

Indexes: `{ trackingNumber: 1 }` unique, `{ type: 1, createdAt: -1 }`,
`{ patient: 1, createdAt: -1 }`, `{ appointment: 1 }`,
`{ "drive.status": 1, "drive.nextAttemptAt": 1 }`.

### 7.2 `DocumentCounter` (`backend/src/models/documentCounterModel.ts`)

```ts
export interface DocumentCounter {
  key: string;   // "RPT-2026"
  seq: number;
}
```

Allocation is one atomic upsert, safe under concurrent requests and process restarts:

```ts
const counter = await DocumentCounter.findOneAndUpdate(
  { key: `${prefix}-${year}` },
  { $inc: { seq: 1 } },
  { new: true, upsert: true, setDefaultsOnInsert: true },
);
```

The counter is never reset mid-year. Deleting documents does not rewind it, so numbers are never
reused.

### 7.3 `GoogleDriveConnection` (`backend/src/models/googleDriveConnectionModel.ts`)

```ts
export interface GoogleDriveConnection {
  key: "clinic";                    // singleton
  connected: boolean;
  email: string;                    // connected Google account
  refreshTokenEncrypted: string;    // secretBox
  rootFolderId: string;             // app-created "AbsoluteCare Documents"
  folderCache: { name: string; id: string }[];  // resolved type/month folders
  connectedAt: Date | null;
  connectedBy: Types.ObjectId | null;
  needsReconnect: boolean;
  lastError: string;
}
```

Why a new model instead of `User.googleCalendar`: the Drive connection belongs to the clinic, not to
whichever admin clicked Connect. If that admin is archived, documents must still upload. Why not
`IntegrationCredential`: that store is for admin-pasted, OTP-guarded secrets; an OAuth refresh token
is obtained through a consent flow and must not appear in the credential editor.

`connected` + `needsReconnect` are separate: `connected` means a token exists, `needsReconnect`
means Google rejected it (401) and an admin must re-consent. The integration card shows both.

## 8. Document types and content

All four share one renderer; only the body builder differs. Every body is assembled from existing
collections, never from client-supplied JSON (the client sends ids and a date range, not content).

### 8.1 `clinic_report` — `RPT-YYYY-NNNNNN`

Source: `getReportData(from, to)` in `adminMonitoringService.ts` (the same data behind the Reports
page). Body sections, in order:

1. Range statement ("1 November 2026 to 30 November 2026", clinic timezone).
2. Clinic summary table: registered patients, new patients in period, patients with a recorded
   session, appointments booked, completion rate, sessions recorded, therapy time, payments
   collected, open balances.
3. Appointments by status table (status, count) with a "no appointments in this period" row.
4. Therapist workload table (therapist, assigned, completed).
5. Sessions by service table (service, sessions, therapy time).
6. Payments by method table (method, visits, collected).
7. Closing note: which collections the figures came from and that open balances are unsettled visits.

Range defaults: current month to date, matching the Reports page's `presetRange('month')`.

### 8.2 `patient_summary` — `PTS-YYYY-NNNNNN`

Source: `User` (patient), optional `Dependent`, `Session` in range, `Appointment` counts.
Request shape: `{ patientId, dependentId?, from, to }`.

Sections:

1. Patient identity block: full name, date of birth, phone, email, address (omit blank fields).
2. Care period statement + total sessions, total therapy time, treating therapists.
3. Sessions table: date, therapist, service, duration, **`patientVisibleNotes` only**.
4. Appointment adherence summary: booked, completed, cancelled, no-show (from appointments in the
   same range).
5. Treating clinician note line: therapist names, no clinical narrative.

Hard rule: `Session.clinicalNotes` is never read by the builder. If someone later adds "include
notes", it must be a new document type with its own permission, not a flag on this one.

### 8.3 `visit_record` — `VIS-YYYY-NNNNNN`

Source: one `Appointment` with patient, dependent, therapist, service populations.

Sections: appointment reference and status; patient (or dependent) identity; therapist; service and
duration; scheduled start/end in clinic time; payment status and amount; appointment notes
(`Appointment.notes`, which is staff-facing but already used in admin views — see §20 for the policy
flag); a compact audit summary (requested, confirmed, completed/rescheduled/cancelled) with actor
roles only, no internal ids.

### 8.4 `receipt` — `RCP-YYYY-NNNNNN`

Source: one paid `Appointment.payment`.

Sections: receipt number (the tracking number), payment date (`recordedAt`), payer name (patient or
dependent), service and visit date, amount paid, method, reference number, "received by" (the staff
member who recorded it, resolved from `payment.recordedBy`), and an explicit "This receipt covers
the visit listed above only." line. Only `payment.status === "paid"` appointments can produce a
receipt; the API returns 409 otherwise.

### 8.5 Data freshness

The PDF is a snapshot. Later edits to the appointment or session do not change an issued PDF; staff
regenerate to get a new tracking number (decision #9). The document record keeps the source ids so
the archive can link back to the live record, but the body is never re-hydrated from them.

## 9. PDF layout specification

One renderer, one letterhead, four bodies. Every document looks like it came from the same clinic.

### 9.1 Page geometry

- A4 portrait (595.28 x 841.89 pt), 48 pt side margins, 118 pt reserved header band, 64 pt reserved footer band.
- Content flows between the bands; a table row is never split across pages (measure with `doc.heightOfString` and start a new page when the next row does not fit).
- Long tables repeat their header row after a page break.
- Font: pdfkit built-in Helvetica (regular / bold) so no font file must ship. If an embedded display face is wanted later, add OFL licensed TTF files under `backend/assets/fonts/` and register them in one place; never fetch fonts at render time.

### 9.2 Header (every page, decision #19)

Left column:

- Clinic logo from `backend/assets/email/logo.png` at 36 pt height when the file exists; otherwise the clinic name wordmark in bold 13 pt.
- Clinic name from `settings.general.clinicName` (fallback "AbsoluteCare Therapy Center").
- Address, phone, email from `settings.general` at 7.5 pt / ink-soft; blank fields are omitted, separators are middle dots.

Right column:

- Document title ("Clinic activity report", "Patient therapy summary", "Visit record", "Payment receipt") at 13 pt bold, right aligned.
- Tracking number in tabular 9 pt with a hairline box around it.
- QR code, 52 x 52 pt, aligned top-right, encoding the verification URL from section 10.
- A 0.5 pt hairline rule spans the full content width under both columns.

### 9.3 Footer (every page)

Three columns on one line, above a 0.5 pt rule:

- Left: `Issued {date} {time} ({timezone}) by {generatedByName} ({role})`.
- Center: `Page {n} of {total}` (computed after pagination with `bufferedPageRange`).
- Right: `Verify: {verificationUrl}` in 7 pt, truncated with an ellipsis if needed.

Second line, centered, 6.5 pt, ink-faint:

> Confidential. Issued by {clinicName}. Authenticity can be checked at {verificationHost}.

### 9.4 Signature block

End of the body, after a 24 pt gap:

- Two 120 pt signature rules side by side: `Issued by` (issuer name, role, date) and `Received by` (blank line for a handwritten signature when the document is handed over).
- A line under the block: `Electronically issued. This document is valid without a handwritten signature; scan the QR code to confirm it.`

### 9.5 Tone and typography

Follow `DESIGN.md` translated to print: warm paper is not printable, so the PDF stays on white with the pine (#14453b) heading colour, clay (#8f3b2f) only for a revoked stamp, and no decorative graphics. Labels are sentence case. Money and counts use tabular figures (pdfkit: fixed-width digits via Helvetica, right aligned). Headings are at most 18 pt; body 9.5 pt; table text 8.5 pt; footer 7 pt.

### 9.6 Date, money and timezone

- All dates and times format in `settings.general.timezone` (default Asia/Manila) using `Intl.DateTimeFormat("en-PH", ...)`.
- Money uses `settings.general.currency` (default PHP) and two decimals, e.g. `PHP 1,250.00`.
- The PDF never prints UTC or an ISO timestamp without an offset; the issue line states the timezone abbreviation.

## 10. Tracking numbers

Format: `{TYPE}-{YYYY}-{NNNNNN}`

| Type | Prefix | Example |
| ---- | ------ | ------- |
| Clinic activity report | `RPT` | `RPT-2026-000123` |
| Patient therapy summary | `PTS` | `PTS-2026-000045` |
| Visit record | `VIS` | `VIS-2026-000891` |
| Payment receipt | `RCP` | `RCP-2026-000210` |

- The year is the clinic-local year at issue time.
- Sequence is per prefix per year, zero padded to six digits. Above 999999 the field widens rather than wraps (the format is `padStart`, not a slice).
- The tracking number is allocated before rendering so it can appear in the header, footer and QR of the same file.
- It is immutable. A correction is a new document with a new number, and the old one links forward via `supersededBy`.
- The number is safe to read aloud and type: uppercase letters, digits and hyphens only.

Human-facing label on the verification page: `Tracking number RPT-2026-000123`. The same string is the filename stem.

## 11. Public verification

### 11.1 QR payload

`{FRONTEND_URL}/verify/{trackingNumber}`. `FRONTEND_URL` is trimmed of a trailing slash. The QR contains no name, id, type, amount or token.

If `FRONTEND_URL` still points at localhost, the QR is generated but the PDF header prints a warning line `Verification URL is not public` and the boot log warns once. Never silently emit an unscannable QR in production.

### 11.2 Endpoint

`GET /verify/:trackingNumber` (mounted before the auth-protected routers; no cookies required).

```ts
// 200
{
  status: "valid" | "superseded" | "revoked",
  documentType: "clinic_report" | "patient_summary" | "visit_record" | "receipt",
  documentLabel: "Clinic activity report",
  trackingNumber: "RPT-2026-000123",
  issuedAt: "2026-11-07T02:14:00.000Z",
  clinicName: "AbsoluteCare Therapy Center",
  supersededBy?: "RPT-2026-000124",
  supersededAt?: "2026-11-08T01:00:00.000Z",
  revokedAt?: "2026-11-09T03:20:00.000Z"
}

// 404, same body shape so the page has one empty state
{ status: "not_found" }
```

Rules:

- No patient name, no appointment id, no amount, no Drive link, no issuer name.
- The lookup is by exact `trackingNumber` (case-insensitive normalisation: uppercase and trim before query).
- `supersededBy` is returned as a tracking number only, never an internal id.
- Rate limit: 30 requests per IP per minute, in-memory fixed window, `429` with `Retry-After: 60`. The app has no global limiter, so this is a small route-local middleware, not a new dependency.
- Unknown and malformed numbers both return the same 404 body (no format oracle beyond the prefix itself).
- Sequential numbers are enumerable by design (decision #10). The mitigation is the minimal payload plus the rate limit; section 20 records this as an accepted residual risk.

### 11.3 Public page (`/verify/:trackingNumber`)

A standalone, unauthenticated page, no staff layout, no nav. Paper-and-pine styling from `DESIGN.md`:

## 12. Google Drive integration

### 12.1 Consent flow

| Step | Detail |
| ---- | ------ |
| Start | `GET /integrations/google-drive/connect` (admin only) builds `https://accounts.google.com/o/oauth2/v2/auth` with `client_id`, `redirect_uri = GOOGLE_DRIVE_REDIRECT_URI`, `response_type=code`, `access_type=offline`, `prompt=consent`, `scope=https://www.googleapis.com/auth/drive.file`, and a signed short-lived `state` (admin id + nonce, same JWT secret, 10 min). |
| Callback | `GET /integrations/google-drive/callback` (unauthenticated, like the Calendar callback) verifies `state`, exchanges the code at `https://oauth2.googleapis.com/token`, fetches the account email from `https://openidconnect.googleapis.com/v1/userinfo`, encrypts the refresh token with `secretBox.encryptSecret`, upserts the singleton connection, and redirects to `{FRONTEND_URL}/staff/admin/settings?section=integrations&drive=connected` (or `&drive=error&reason=...`). |
| Status | `GET /integrations/google-drive/status` (admin/secretary) returns `{ connected, email, connectedAt, needsReconnect, rootFolderName, lastError }`. Never returns the token. |
| Disconnect | `POST /integrations/google-drive/disconnect` (admin only, no OTP in v1 because it is not a credential write) clears the token and sets `connected: false`. Already-issued documents keep their Drive links. |

### 12.2 Root folder

On first successful upload, if `connection.rootFolderId` is blank, create `AbsoluteCare Documents` with `mimeType: application/vnd.google-apps.folder`, store the id, and log the name only. If `GOOGLE_DRIVE_ROOT_FOLDER_ID` is set and no stored root exists, use it verbatim, but a `404` means the folder was not created by this app (a constraint of `drive.file`) and must surface as the actionable error: "The configured Drive folder is not visible to this app. Clear GOOGLE_DRIVE_ROOT_FOLDER_ID so the app can create its own folder."

### 12.3 Folder resolution

Type folders: `Clinic reports`, `Patient summaries`, `Visit records`, `Receipts`. Month folders: `YYYY-MM` in clinic time. Resolve with a search by name under the parent, reuse on hit, create on miss, and cache `{ name, id }` on the connection document with a 24 h in-memory TTL. Name collisions are impossible because the search is scoped to the parent. Concurrency: two simultaneous uploads may both create a folder; the loser adopts the first result on the next search, and duplicate empty folders are harmless. To reduce that window, folder creation happens behind a promise-per-name map inside `driveService`.

### 12.4 Upload

```
POST https://www.googleapis.com/upload/drive/v3/files
  ?uploadType=multipart&supportsAllDrives=true&fields=id,webViewLink,name,size
Authorization: Bearer <access token>
Content-Type: multipart/related; boundary=<boundary>

--<boundary>
Content-Type: application/json; charset=UTF-8

{
  "name": "RPT-2026-000123_2026-11-07.pdf",
  "parents": ["<month folder id>"],
  "mimeType": "application/pdf",
  "description": "AbsoluteCare document RPT-2026-000123",
  "appProperties": { "trackingNumber": "RPT-2026-000123", "documentType": "clinic_report" }
}
--<boundary>
Content-Type: application/pdf

<bytes>
--<boundary>--
```

- Filename: `{trackingNumber}_{yyyy-mm-dd}.pdf`. **No patient name, no service name, no clinic report period** in the filename or description.
- `appProperties` are searchable by the app and carry no personal data.
- Access token is fetched per upload from the stored refresh token, cached in memory until 60 s before `expires_in`, never logged.
- Timeout 10 s via `AbortSignal.timeout`.

### 12.5 Token refresh

`POST https://oauth2.googleapis.com/token` with `grant_type=refresh_token`. On `400`/`401`, mark `needsReconnect = true` and stop retrying (a revoked grant never heals). On success, cache the access token. Refresh failures do not delete documents or tracking numbers.

### 12.6 Failure classification

| Condition | Drive status | Retry? | Staff-facing message |
| --------- | ------------ | ------ | -------------------- |
| No connection / disabled | `pending` | no | "Google Drive is not connected. An admin can connect it in Settings, Integrations." |
| `401`, invalid_grant, revoked token | `pending` + `needsReconnect` | no (until re-consent) | "Google Drive access was revoked. Reconnect the clinic account." |
| `403 storageQuotaExceeded` | `failed` | no | "The clinic Google Drive is out of storage. Free space or change the account." |
| `403 insufficientFilePermissions` | `failed` | no | "The app cannot write to the configured folder." |
| `404` folder | `pending` | yes, after clearing the folder cache and re-creating | "The Drive folder moved. The app will recreate it." |
| `429`, `5xx`, network, timeout | `pending` | yes | "Google Drive is temporarily unavailable. Retrying." |
| `400` other | `failed` | no | "Google Drive rejected this file." + Google's message, truncated |

Every transition updates `drive.attempts`, `lastAttemptAt`, `lastError` and `nextAttemptAt`. `lastError` is stored for staff and must never contain the token or the file bytes.

## 13. Background sync queue

`documentSyncJob.ts` mirrors `appointmentReminderJob.ts` and is started in `app.ts` with
`setInterval(runDocumentSyncJob, 5 * 60 * 1000)` plus one immediate run after `connectDB()`.

Per run:

1. Bump the due window by setting `nextAttemptAt` on rows that have none (legacy safety).
2. Select up to 10 documents: `{ status: "issued", "drive.status": { $in: ["pending", "failed"] }, "drive.attempts": { $lt: 5 }, "drive.nextAttemptAt": { $lte: now } }`, oldest first.
3. For each: skip when `needsReconnect` or `googleDriveEnabled` is false; otherwise attempt upload and update the row.
4. Backoff on retryable errors: 1 min, 5 min, 15 min, 1 h, 6 h. After the 5th attempt set `drive.status = "failed"` (terminal, manual retry only).
5. Log one line per transition: tracking number, attempt, outcome code. Never log file contents or tokens.

Single-instance assumption: this app runs one Node process behind a supervisor (the existing
self-restart feature already assumes that). Do not build a distributed lock; if a second instance is
ever added, wrap the select in a `findOneAndUpdate` lease with `drive.lockedAt`.

Manual retry (`POST /documents/:id/retry`) resets `drive.attempts = 0`, clears `lastError`, sets
`nextAttemptAt = now`, and moves a terminal `failed` row back to `pending`.

## 14. API contract

All staff endpoints sit behind `protectRoute`; role checks are per endpoint. Responses are JSON
except the download, which streams bytes.

### 14.1 `POST /documents`

Zod schema (`backend/src/schemas/documentSchema.ts`):

```ts
documentCreateSchema = z.discriminatedUnion("type", [
  z.object({ type: z.literal("clinic_report"), from: isoDate, to: isoDate }),
  z.object({
    type: z.literal("patient_summary"),
    patientId: objectId,
    dependentId: objectId.optional(),
    from: isoDate,
    to: isoDate,
  }),
  z.object({ type: z.literal("visit_record"), appointmentId: objectId }),
  z.object({ type: z.literal("receipt"), appointmentId: objectId }),
]);
```

Validations: `from <= to`, range at most 366 days, patient/dependent relationship verified (the
dependent must belong to the patient), appointment must exist. 201 returns:

```ts
{ document: {
    id, trackingNumber, type, title, status,
    issuedAt, generatedBy: { name, role },
    sizeBytes, sha256,
    drive: { status, webViewLink, attempts, lastError },
    verifyUrl
} }
```

`pdf` is never included. The inline upload attempt happens before responding so a healthy Drive
returns `drive.status: "uploaded"` immediately; a failure returns `pending` or `failed` per section
12.6 and the request still succeeds.

### 14.2 `GET /documents`

Query: `type?`, `patientId?`, `appointmentId?`, `driveStatus?`, `status?`, `from?`, `to?`, `page=1`,
`limit=20` (max 50). Admin sees all; secretary and therapist see documents they generated
(`generatedBy = req.user.userId`). Response `{ documents, pagination: { page, pages, total } }`,
newest first, no `pdf` field. Aggregation-free: a plain indexed query with `.select("-pdf")`.

### 14.3 `GET /documents/:id`

Metadata plus `verifyUrl` and `drive.webViewLink`; own-document rule for non-admins; 404 for any
other id (no existence oracle).

### 14.4 `GET /documents/:id/file`

Streams `application/pdf` with `Content-Disposition: attachment; filename="<tracking>_<date>.pdf"`
and `Cache-Control: private, no-store`. Sets `X-Content-Type-Options: nosniff`. Works with no Drive
connection. Role/lookup rules same as 14.3; a patient cannot call this.

### 14.5 `POST /documents/:id/retry`

Admin or secretary. 409 when `drive.status === "uploaded"`. Returns the updated metadata.

### 14.6 `POST /documents/:id/revoke`

Admin only. Body `{ reason: string }` (Zod, 4-500 chars, required). Sets `status = "revoked"`,
`revokedAt`, `revokedBy`, `revokeReason`. Does not delete the Drive file or the bytes. 409 if
already revoked. Returns the updated metadata. The verification page immediately reflects it.

Superseding is not a client action: it is written by `createDocument` when the request targets the
same source (same `type` + `patientId`/`appointmentId` + identical range) and a previously issued
document exists. The new record links `supersedes`, and the old record gets `supersededBy` and
`status = "superseded"` in the same save pair. A document can be both revoked and superseded;
the verification page reports revoked first.

### 14.7 `GET /verify/:trackingNumber`

Public, rate-limited, shape in section 11.2. Mounted in `app.ts` before the `/admin` routers and
before the SPA fallback. It must never require a cookie, and it must not use `protectRoute`.

### 14.8 Drive endpoints

`GET /integrations/google-drive/connect` (admin), `GET /integrations/google-drive/callback`
(public), `GET /integrations/google-drive/status` (admin, secretary),
`POST /integrations/google-drive/disconnect` (admin),
`POST /integrations/google-drive/test` (admin) which uploads a one-page test PDF to
`AbsoluteCare Documents/_connection-test/`, returns the file name and webViewLink, then trashes it
(`DELETE /drive/v3/files/:id`) so the folder stays clean. Failure messages reuse section 12.6.

## 20. Security and privacy

1. **No PII in Drive metadata or filenames.** Type/month folders, tracking-number filenames, generic descriptions. A leaked Drive folder reveals that documents exist, not who they concern.
2. **The public page reveals no patient data.** It answers only "was this issued, and is it still current?". This is the compensating control for sequential tracking numbers.
3. **Tracking numbers are enumerable.** Accepted residual risk of decision #10. Mitigations: minimal payload, 30/min/IP limit, uniform 404s, no bulk list endpoint, no patient name in the response. If the clinic later wants unguessable links, the QR can switch to a random token column without changing the printed format.
4. **PDF bytes are private.** Download is authenticated and role-scoped; responses use `Cache-Control: private, no-store`; no public bucket or static serving of documents.
5. **Clinical notes never enter a PDF.** The summary builder selects `patientVisibleNotes` explicitly and must not reuse a `find()` that returns the whole session document without projection.
6. **Drive tokens at rest** use AES-256-GCM via `secretBox`, are excluded from every response, and are never logged. `lastError` is sanitised to a short message.
7. **Revocation is not deletion.** Revoke marks status for verification; the bytes and Drive file remain for audit. A future retention policy is out of scope.
8. **No CSRF surface added for verification** (GET only). Staff POSTs are cookie-authenticated exactly like the rest of the app; no new origin rules.
9. **Drive scope is least privilege** (`drive.file`). The app cannot read the clinic's other files.
10. **Document generation is read-only on clinical data.** It writes only to the document collections; no appointment, session, payment or user record is mutated.
